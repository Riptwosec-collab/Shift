# Shift Command Center v6.3 Design

Date: 2026-10-01
Repository: `Riptwosec-collab/Shift`
Target branch: `main`
Production model: Cloudflare native Git auto-deploy from `main`

## 1. Goal

Upgrade the existing Shift Command Center from v6.2.1 into a smoother, more useful operations dashboard without changing the employee roster or October 2026 shift schedule data.

The release must improve three areas together:

1. Performance from the first loading frame through normal navigation.
2. Operational usefulness of Daily, Analytics, Team Network, and search/navigation flows.
3. Visual quality while keeping the futuristic neon command-center identity.

The production output remains a single `index.html` so the existing Cloudflare native deployment flow does not need to change.

## 2. Non-goals and invariants

The following are explicitly out of scope:

- Do not change employee names.
- Do not change any `D`, `N`, or `O/OFF` schedule values.
- Do not add account/login/backend requirements.
- Do not add Remember Last View or persist the last page, selected date, selected employee, or visual mode across reloads.
- Do not add a GitHub Actions deployment workflow. Cloudflare remains responsible for native deployment.
- Do not replace the current overall visual identity with a new design system.

Status semantics remain:

- `D` = Day shift, red.
- `N` = Night shift, blue.
- `OFF` = Off, green.

All user-facing off-duty labels must display `OFF`, even if the internal schedule representation remains `O`.

## 3. Architecture

### 3.1 Development source structure

The refactor should separate responsibilities during development:

```text
src/
  data.js
  core.js
  cache.js
  performance.js
  loader.js
  overview.js
  daily.js
  person.js
  month.js
  analytics.js
  network.js
  risk.js
  command-palette.js
  mobile.js
  styles.css
```

Responsibilities:

- `data.js`: immutable employee and schedule data plus date helpers.
- `core.js`: app state, view switching, shared DOM utilities, event bus, selected day/person state.
- `cache.js`: derived-data cache and invalidation rules.
- `performance.js`: visual quality mode, idle scheduling, visibility-based animation control, throttling.
- `loader.js`: 3-second boot experience and transition into the dashboard.
- `overview.js`: overview metrics, timeline, roster summaries, month preview.
- `daily.js`: detailed daily operations view.
- `person.js`: employee-focused schedule and workload view.
- `month.js`: monthly heatmap/table.
- `analytics.js`: workload, staffing, activity chart, team averages.
- `network.js`: Team Network 2.0 relations and interactions.
- `risk.js`: staffing-risk rules and derived alerts.
- `command-palette.js`: `/` and `Ctrl+K` command/search interface.
- `mobile.js`: swipe, sticky summaries, safe-area and responsive behavior.
- `styles.css`: design tokens, component styles, responsive rules, quality-mode overrides.

### 3.2 Production output

The build process combines the development modules into one standalone `index.html` with no external runtime library requirement.

The deployment contract stays:

```text
source modules -> build -> index.html -> push main -> Cloudflare native auto-deploy
```

The modular source is for maintainability; the deployed file remains self-contained.

## 4. Application state and data flow

The app keeps a small in-memory state object:

```text
activeView
selectedDay
selectedPerson
selectedRosterPerson
visualMode
renderedViews
cacheVersion
```

`visualMode` always starts as `BALANCED` on each page load and is not stored in `localStorage`.

State changes emit narrow update events instead of forcing whole-app renders. Example:

```text
selectedDay changes
  -> Overview metrics update
  -> Daily view updates only if mounted/visible
  -> Analytics selected-day marker updates only if mounted
  -> Network updates only when its displayed relation depends on selected day
```

Views that have never been opened must not be fully rendered at startup.

## 5. Performance engine

### 5.1 Startup strategy

Before the loader disappears, the app may perform only lightweight work:

- Parse the static schedule dataset.
- Initialize minimal app state.
- Build small shared lookup tables.
- Render the visible Overview shell and essential first-screen metrics.
- Register event listeners.

The app must not eagerly render Daily, Person, Month, Analytics, or full Team Network content during loader animation.

Heavy derived work should be deferred until after the first interactive frame using `requestIdleCallback` when available, with a `setTimeout` fallback.

### 5.2 Lazy rendering

Each view gets a first-render flag:

- `overview`: rendered on startup.
- `daily`: first render on first Daily navigation.
- `person`: first render when Person is opened or a person is selected.
- `month`: first render on first Month navigation.
- `analytics`: first render on first Analytics navigation.

Subsequent visits update only data that changed.

### 5.3 Derived-data cache

Cache the following immutable-for-session calculations:

- D/N/OFF counts per day.
- Working count and coverage per day.
- Per-person D/N/OFF totals.
- Per-person longest work streak.
- Per-person longest night streak.
- Team averages.
- Pairwise shift-overlap matrix.
- Pairwise same-D and same-N counts.
- Handoff counts.
- Monthly busiest/least-staffed days.

Because schedule data is static for this dashboard, these cache entries do not need continuous invalidation. UI selection state is never stored in the cache as schedule data.

### 5.4 Rendering and event rules

- Use `requestAnimationFrame` for pointer-based visual updates.
- Do not read layout repeatedly inside the same frame when values can be reused.
- No global MutationObserver may repeatedly scan the full body for OFF-label normalization.
- OFF formatting should happen during component rendering.
- Stop or pause nonessential animations when their element is outside the viewport using `IntersectionObserver` where practical.
- Page-hidden state should pause nonessential requestAnimationFrame loops.
- Avoid continuous animations on large blurred fixed layers after the loader closes.

### 5.5 Visual quality modes

Add a visible control with three session-only modes:

- `HIGH`: full glow, richer motion, stronger blur, full Team Network effects.
- `BALANCED`: default; preserves the premium look with reduced continuous repaint cost.
- `ECO`: minimal blur, static ambient background, reduced glow and no decorative continuous motion.

Rules:

- Default every reload: `BALANCED`.
- Do not persist the mode.
- Changing the mode updates CSS classes/tokens, not component data.
- Mobile may automatically cap expensive effects even if the user selects HIGH, but the label remains the selected mode.

## 6. Loader v6.3

### 6.1 Duration

The loader should remain visible for approximately 3 seconds so the animation can be seen intentionally.

Timing contract:

- Target visible duration: `3000 ms`.
- Fade/reveal transition: approximately `250-350 ms` and included at the end of the sequence.
- Safety hard exit: `3600 ms` maximum.

The loader must never wait indefinitely for a secondary view, analytics calculation, browser font, or decorative animation.

### 6.2 Visual sequence

Use the current cyber HUD direction, upgraded to a smoother sequence:

1. `CORE INITIALIZE`
2. `SHIFT MATRIX VERIFY`
3. `COMMAND GRID LINK`
4. `INTERFACE READY`

Visual elements:

- Multi-ring cyan/blue/violet/orange orbit.
- Central energy core.
- Lightweight radar sweep.
- Neon progress rail.
- Four phase indicators.
- Small system status cards for UI, Matrix, and Runtime.
- Subtle hex/grid background.
- Final `READY` state before reveal.

Only `transform` and `opacity` animations should run every frame. Avoid animated heavy blur, full-screen filter, or continuously changing large gradients.

### 6.3 Loader progress behavior

Progress is time-driven for presentation, not a fake dependency blocker.

Suggested pacing:

- 0-20%: 0-500 ms
- 20-50%: 500-1300 ms
- 50-80%: 1300-2200 ms
- 80-100%: 2200-3000 ms

At 100%, set status to `READY`, then reveal the already-prepared Overview.

## 7. Daily Operations upgrade

The Daily page becomes the main operational view.

For the selected date, show a top summary:

```text
D: x | N: y | OFF: z | Coverage: n%
```

Add these sections:

### 7.1 Shift roster

- Full D roster.
- Full N roster.
- Full OFF roster.
- Counts remain visible in section headers.

### 7.2 Day-over-day comparison

Compare selected day with both previous and next day:

- D delta.
- N delta.
- OFF delta.
- Working-count delta.
- Coverage delta.

For the first or last day of the month, the missing comparison side shows `N/A` rather than wrapping into another month.

### 7.3 Shift transitions

Identify employees whose status changes between adjacent days, for example:

```text
D -> N
N -> OFF
OFF -> D
```

This is descriptive only and does not modify the schedule.

### 7.4 Streak indicators

Show:

- Current consecutive working-day streak for each working employee.
- Current consecutive night streak where applicable.
- Longest monthly streak in the employee detail drawer.

## 8. Staffing Risk engine

Risk alerts are deterministic rules derived from the fixed schedule. They are informational, not recommendations to change the schedule.

Default rule thresholds:

- `LOW_STAFFING`: working staff < 6 of 10.
- `LOW_NIGHT_COVERAGE`: N staff < 2.
- `CONSECUTIVE_WORK`: employee works 3 or more consecutive days.
- `LONG_NIGHT_STREAK`: employee has 3 or more consecutive N shifts.
- `D_N_IMBALANCE`: absolute daily difference between D and N staff >= 3.
- `HIGH_OFF_COUNT`: OFF staff >= 5.

Thresholds must be defined in one constants object so they are easy to adjust later.

Risk UI:

- Small severity badge.
- Short reason.
- Affected date/person.
- No alarm sound.
- No automatic schedule mutation.

Severity:

- Info: workload/streak observation.
- Warning: low night coverage, D/N imbalance.
- Critical: low staffing.

## 9. Team Network 2.0

The relationship model uses pairwise schedule overlap for the month.

For each pair, calculate:

- `sameShift`: same working shift on the same date.
- `sameD`: both D on the same date.
- `sameN`: both N on the same date.
- `handoff`: one employee changes off a working shift while the other enters a working shift on the next day.
- `strength`: normalized relationship score.

Strength formula:

```text
raw = sameShift * 2 + handoff
strength = round(raw / maxPairRaw * 100)
```

If all pair scores are zero, strength is 0 to avoid division by zero.

### 9.1 Interaction

- Click any teammate node to make that employee the network center.
- Center click opens the employee detail view/drawer.
- Edge thickness maps to strength.
- Edge opacity maps to strength.
- Only the strongest relevant relationships are shown at once to avoid overcrowding.

Desktop maximum visible outer nodes: 6.
Tablet maximum: 5.
Mobile maximum: 4.

The full relation list remains available below the graph so hidden nodes are not lost.

### 9.2 Details

Hover/focus/tap detail should show:

```text
Same Shift: n
Same D: n
Same N: n
Handoff: n
Strength: n%
```

Also identify `Top teammate` for the selected center employee.

## 10. Analytics and Workload Balance

Per employee show:

- D count.
- N count.
- OFF count.
- Total working days.
- Night percentage among working days.
- Longest working streak.
- Longest night streak.
- Difference from team average working days.

Team summary includes:

- Average working days.
- Average N shifts.
- Highest/lowest monthly workload values.
- Busiest and least-staffed dates.
- Monthly D/N/OFF totals.

The existing daily activity chart remains but becomes interactive.

## 11. Interactive Timeline

Clicking a day in Overview timeline or Analytics activity chart calls one shared `setSelectedDay(day)` path.

That path updates only already-mounted dependent components.

Expected synchronization:

```text
Timeline day click
  -> selectedDay
  -> Overview D/N/OFF metrics
  -> selected-day visual marker
  -> Daily content if Daily is mounted
  -> Analytics detail if Analytics is mounted
  -> staffing risk summary for selected date
```

No duplicated independent selected-day state is allowed.

## 12. Command Palette

Open with either:

- `/` when focus is not in an input/textarea.
- `Ctrl+K` / `Cmd+K`.

Supported query categories:

- Date: `15`, `15 ต.ค.`, `15 Oct`.
- Employee name fragments.
- `day`, `D`, `กลางวัน`.
- `night`, `N`, `กลางคืน`.
- `off`, `OFF`.
- View names: `overview`, `daily`, `person`, `month`, `analytics`, `team`.

Results should be keyboard navigable with Arrow Up/Down, Enter, and Escape.

The palette must not persist query history across reloads.

## 13. Mobile UX

### 13.1 Navigation

- Keep bottom navigation.
- Respect iPhone safe-area insets.
- Minimum touch target approximately 44 px.

### 13.2 Daily

- Horizontal swipe changes selected day.
- Sticky compact D/N/OFF/Coverage strip remains visible while scrolling Daily.

### 13.3 Month

- Horizontal overflow uses snap-friendly scrolling rather than compressing every day cell to unreadable width.

### 13.4 Team Network

- Reduce visible node count automatically.
- Prevent labels/tooltips from escaping the card.
- Tap replaces hover-only interactions.

### 13.5 Performance

On narrow/mobile layouts:

- Disable nonessential full-screen decorative movement.
- Reduce blur radius and shadow spread.
- Keep loader orbit smooth and visually complete.

## 14. Error handling and safeguards

The dashboard is static and should fail soft.

- If a derived analytics calculation fails, Overview must still render.
- If Team Network enhancement fails, fall back to the basic employee relation list.
- Loader hard exit always reveals the dashboard shell by 3600 ms.
- Missing DOM target should skip that component update instead of throwing globally.
- Risk calculations with missing adjacent dates treat the unavailable side as absent, not as another month.
- No use of `document.write()`.
- No runtime gzip/decompression handoff.
- No infinite MutationObserver loop.

## 15. Accessibility

- Keyboard navigation for command palette, date controls, tabs, Team Network nodes, and modal/drawer controls.
- Visible focus state retained.
- Do not rely on red/blue/green color alone; retain D/N/OFF text labels.
- Loader text remains readable independent of animation.
- `prefers-reduced-motion` reduces decorative motion but does not shorten the 3-second loader timing unless the user skips/reloads through browser behavior.

## 16. Testing strategy

### 16.1 Data integrity tests

Verify exact employee names and all 31 schedule characters per employee are unchanged from v6.2.1.

Verify derived counts satisfy, for every day:

```text
D + N + OFF = 10
```

### 16.2 Unit-level logic tests

Test:

- Daily D/N/OFF counts.
- Coverage calculation.
- Consecutive work streak.
- Consecutive night streak.
- Risk thresholds.
- Pair overlap and strength calculations.
- Handoff calculation.
- Command-palette parser.

### 16.3 UI behavior tests

Test:

- Loader reaches READY and exits around 3 seconds.
- Hard exit works at <= 3600 ms.
- Overview is usable after loader.
- Daily/Person/Month/Analytics lazy-render on first visit.
- Repeated navigation does not duplicate listeners or nodes.
- Timeline/chart selection stays synchronized.
- Team Network node click changes center.
- HIGH/BALANCED/ECO changes effects without changing data.
- Visual mode resets to BALANCED after reload.
- No last-view/date/person state is restored after reload.

### 16.4 Performance checks

Acceptance targets are practical browser-level checks rather than strict lab benchmarks:

- No visible long task caused by rendering all views at startup.
- Loader animation remains smooth while startup preparation runs.
- No continuous body-wide MutationObserver rescans.
- No page-unresponsive warning during ordinary navigation.
- Pointer movement does not trigger uncontrolled layout/repaint loops.
- Offscreen decorative animations are paused/reduced where implemented.

### 16.5 Responsive checks

Test at minimum:

- 1920x1080 desktop.
- 1366x768 laptop.
- 1024px tablet width.
- 390px iPhone-class width.

Verify no Team Network overflow and no critical control is covered by bottom navigation or safe-area insets.

## 17. Migration approach

Implementation should proceed by extracting logic from the existing single HTML rather than rewriting employee/schedule data by hand.

Recommended migration order:

1. Add source modules and copy current immutable data exactly.
2. Add tests that lock employee/schedule data before feature changes.
3. Introduce core state and cache layer.
4. Move Overview to the new render model and verify parity.
5. Add 3-second loader/performance engine.
6. Migrate Daily, Person, Month, Analytics one view at a time.
7. Add risk engine and Team Network 2.0.
8. Add command palette and mobile refinements.
9. Bundle to standalone `index.html`.
10. Run data-integrity, syntax, behavior, and responsive checks before pushing production output.

At each migration stage, the existing UI should remain functional enough to compare against the previous version.

## 18. Release acceptance criteria

v6.3 is complete only when all of the following are true:

- Loader visibly runs for approximately 3 seconds and stays smooth.
- Loader cannot trap the user beyond the hard-exit limit.
- Overview becomes interactive without eager rendering of all other views.
- Daily operations includes D/N/OFF, coverage, comparisons, transitions, streaks, and risk alerts.
- Team Network 2.0 exposes same shift, same D, same N, handoff, and strength metrics.
- Analytics includes workload balance and streak metrics.
- Timeline and activity-chart date selection use one shared selected-day state.
- Command palette supports dates, employees, shifts, and view navigation.
- Mobile view keeps navigation, summary, network, and month table usable without overflow.
- HIGH/BALANCED/ECO modes work and default to BALANCED on every reload.
- No Remember Last View behavior exists.
- Employee names and every schedule value are unchanged.
- Production build is a standalone `index.html` compatible with the existing Cloudflare native Git auto-deploy flow.
