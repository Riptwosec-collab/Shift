# Shift Command Center v6.5 — Sharp UI + Smooth Boot + TH/EN

## Status
Approved design basis for implementation planning.

## Intent
Upgrade the existing v6.4 Shift Command Center without redesigning or removing the approved legacy UI structure. The v6.4 layout, information architecture, panels, navigation, schedule data, employee names, and features remain intact. v6.5 improves visual sharpness, typography, startup smoothness, motion efficiency, and adds complete Thai/English UI support.

## Non-negotiable constraints
- Preserve all v6.4 panels, views, controls, schedule data, employee names, and existing features.
- Do not alter the October 2026 / 2569 shift schedule.
- Do not replace the legacy visual shell with a new layout.
- Do not remove visual structures to gain performance; performance modes may reduce effects and motion, but the information/UI structure remains present.
- Keep the production artifact deployable through the existing standalone `index.html` / Cloudflare flow.
- Preserve HIGH/BALANCED/ECO mode switching and make the modes substantially more distinct than v6.4.

## 1. Visual quality and sharpness

### Goal
Make the dashboard feel more premium, sharp, and futuristic while improving legibility.

### Design rules
- HUD borders, matrix lines, chart strokes, network links, badges, and separators use crisp 1px rendering where appropriate.
- Reduce large diffuse blur fields that soften nearby text or create unnecessary repaint pressure.
- Use layered glow with tighter radii instead of oversized bloom.
- Keep the established cyan / blue / violet cyber identity.
- Maintain the original cyber city, hero scene, D/N/OFF cards, roster cards, Insights, Team Network, Month Matrix, Daily, Person, Month, and Analytics views.
- Prefer transform/opacity based visual motion over layout-affecting animation.
- Improve chart and matrix contrast without changing underlying data.
- Use `font-variant-numeric: tabular-nums` for KPI and schedule numbers to avoid visible width jitter.

## 2. Typography system

### Goal
All Thai and English text must be clear, comfortably readable, and visually consistent.

### Font stacks
Use local/system-first stacks to avoid blocking startup on remote font downloads.

Thai-oriented stack:
`Leelawadee UI`, `Noto Sans Thai`, `Tahoma`, `Segoe UI`, sans-serif.

English-oriented stack:
`Inter`, `Segoe UI`, system-ui, sans-serif.

The runtime language may choose the preferred stack while retaining safe fallbacks.

### Typography requirements
- Replace scattered tiny 6–8px text where it contains meaningful information.
- Body/detail text target: approximately 10–12px minimum on desktop, larger where space allows.
- Important labels: approximately 11–13px.
- Section titles: approximately 16–20px.
- Preserve large hero/KPI hierarchy.
- Increase line-height for Thai text.
- Do not apply aggressive letter-spacing to Thai copy.
- Keep secondary/tertiary text visibly distinct but readable against dark surfaces.
- Ensure mobile font sizes do not collapse below practical readability.

## 3. Smooth boot and first-load pipeline

### Goal
The loading experience should look smooth from the first frame and avoid visible stutter when the main dashboard appears.

### Startup sequence
1. Load critical document and CSS.
2. Show compositor-friendly loader.
3. Initialize schedule/cache/state while heavy background effects remain suspended.
4. Prepare the first visible view only.
5. Complete the loader target sequence.
6. Reveal the main UI.
7. Enable the selected performance-mode effects after the first frame is stable.
8. Lazy-render non-active views on demand.

### Requirements
- Keep the approved loader experience and timing target unless implementation evidence requires a small tuning change.
- Loader progress must prefer transform-based animation rather than repeated layout-width writes.
- Do not run ambient drift, parallax, expensive network animation, and other continuous visual work behind the loader.
- Batch DOM updates and use `requestAnimationFrame` for frame-sensitive operations.
- Non-active views must not perform full rendering at startup.
- Mouse/parallax tracking must be frame-throttled.
- Avoid runtime decompression and `document.write` mechanisms.
- Avoid network font dependencies during boot.

## 4. Performance modes — visibly distinct profiles

The three modes must differ substantially in visual intensity and runtime cost. The distinction must be immediately noticeable when switching modes.

### HIGH — Full Cyber Experience
HIGH is the premium/full visual target.

- Full cyber glow and depth.
- Ambient cyan/blue/violet movement.
- Grid movement / scan effects.
- Hero parallax and scene response.
- Network link motion, radar/orbit/pulse effects where already part of the design.
- Stronger glass/backdrop blur.
- Rich hover lighting and panel depth.
- Full decorative motion budget.
- All structural UI remains unchanged.

### BALANCED — Calm Cyber
BALANCED must look clearly calmer than HIGH, not merely run the same animations more slowly.

- Reduce glow radius and intensity significantly.
- Reduce backdrop blur and expensive glass effects.
- Disable continuous hero parallax.
- Disable or freeze selected scan/grid layers; retain only a limited number of important animated accents.
- Ambient background movement becomes minimal or mostly static.
- Network animation becomes slow/minimal; avoid continuous multi-layer pulse behavior.
- Hover effects use shorter/lighter shadows and less bloom.
- Keep all panels, graphics, lines, cards, charts, and information visible.
- Retain the cyber design language while visually communicating a lower-cost mode.

### ECO — Crisp Static HUD
ECO must be dramatically different from HIGH and optimized for low continuous GPU activity.

- No continuous decorative animation after initial transitions.
- No ambient drift.
- No scan-beam loop.
- No parallax.
- No continuous network dash/orbit/pulse animation.
- Backdrop blur disabled or reduced to near-zero.
- Glow and box-shadow intensity substantially reduced.
- HUD borders, matrix, chart strokes, badges, cyber scene structures, and information remain visible as static artwork.
- Hover transitions are short and simple.
- Prefer solid/translucent fills over costly blurred glass.
- Keep all content and controls functional.

### Mode behavior
- Switching modes must not reload the page.
- Switching modes must not change schedule/state/data.
- Performance mode remains an in-memory runtime preference unless a later requirement explicitly changes persistence.
- Mode-specific CSS/runtime hooks should be centralized rather than scattered across feature code.

## 5. Thai / English bilingual system

### Goal
Provide full UI language switching for Thai and English without duplicating the application shell.

### UI
Add a compact language control in the existing command area:
`TH | EN`

It must fit the legacy command bar without restructuring the overall layout.

### Architecture
Use one UI and a centralized dictionary/i18n layer.

Recommended shape:
- `i18n.th.*`
- `i18n.en.*`
- translation helper for static and dynamic copy
- locale-aware date/status formatting

Do not create separate Thai and English page trees.

### Translation scope
Translate all user-facing application copy, including:
- navigation
- view titles
- labels
- buttons
- tooltips
- empty states
- search and command palette copy
- Daily Operations details
- Staffing Risk text
- Team Network relation labels
- Workload/Analytics labels
- Month/Person view copy
- loader phases where appropriate
- mobile navigation/sticky summaries
- date/status sentences and dynamic descriptions

### Data that must not be translated or modified
- employee names
- shift schedule values
- internal status codes D / N / O where code identity is required
- source identifiers or technical constants

### Locale formatting
Thai example:
`9 ตุลาคม 2569`

English example:
`9 October 2026`

Dynamic examples:
- `ร่วมกะ 3 คน` → `3 teammates on the same shift`
- `ทำงานต่อเนื่อง 5 วัน` → `5-day work streak`

### Language persistence
- Default language: Thai.
- The selected language should be remembered locally for the next visit.
- Language persistence must store only the language preference and must not mutate schedule/application data.
- Language switching must be instant and must not reload the page.

## 6. Interaction and accessibility

- Maintain keyboard navigation and current command-palette shortcuts.
- Language and mode controls must have clear focus states and accessible labels.
- Motion reduction preferences should still be respected.
- Text contrast should be improved where the current muted copy is too faint.
- Avoid relying on color alone for critical status meaning.

## 7. Mobile behavior

- Preserve v6.4 mobile navigation and safe-area handling.
- Improve Thai/English wrapping and prevent labels from clipping.
- Keep minimum tap targets practical.
- ECO should be especially suitable for lower-power mobile hardware.
- Language switching must update mobile navigation and dynamic content immediately.

## 8. Performance and rendering strategy

- Keep lazy rendering and cache behavior from v6.4.
- Use centralized visual-mode state.
- Separate structural rendering from decorative effects so BALANCED/ECO can reduce cost without removing content.
- Avoid repeatedly rebuilding unchanged DOM when only language or visual mode changes.
- Cache derived schedule metrics independent of language.
- Translate presentation strings at render time or through lightweight binding, not by recomputing schedule analytics.

## 9. Validation and regression gates

The implementation plan must include automated tests/gates for:

### Visual structure
Verify the v6.4 legacy structures remain present:
- command bar
- hero cyber scene
- D/N/OFF cards
- timeline
- roster panels
- insights
- team network
- month matrix
- Daily / Person / Month / Analytics views

### Typography/i18n
- TH is the default for a fresh client.
- TH ↔ EN switch works without reload.
- language persistence restores the selected locale.
- known UI strings are covered by the dictionary.
- employee names and schedule strings remain unchanged.
- English dates use 2026 and Thai dates use 2569 as specified.

### Performance modes
- HIGH, BALANCED, ECO each have distinct profiles.
- BALANCED disables/reduces materially more effects than HIGH.
- ECO contains no continuous decorative animation after startup.
- Structural UI remains visible in all modes.
- switching modes does not mutate schedule state.

### Boot/performance
- first view only is mounted/rendered at startup.
- heavy effects remain suspended during loader.
- no runtime decompression/document.write.
- build remains standalone.

### Production/Cloudflare
- generated `index.html` matches source build.
- Cloudflare asset/deploy safeguards remain valid.
- direct deploy must not accidentally package `node_modules` or other non-production assets.

## 10. Definition of done

v6.5 is complete when:
- the dashboard visibly preserves the approved v6.4 layout and features;
- graphics are sharper and cleaner without sacrificing the cyber identity;
- Thai and English typography are readable across desktop/mobile;
- startup and loader transition are smooth without concurrent heavy rendering;
- TH/EN works across static and dynamic UI with local language persistence;
- HIGH/BALANCED/ECO are immediately distinguishable in both appearance and runtime cost;
- all schedule/employee invariants pass;
- full build, tests, production artifact verification, and Cloudflare deployment gates pass.
